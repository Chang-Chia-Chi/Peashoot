# Resume matches a continued request; the default rules do not change

Status: Proposed — built pending the owner's confirmation

Spike 1 (`docs/research/claude-code-stream-drop-retry.md`, issue #2) measured Claude Code 2.1.278 against the real provider through Peashoot. A drop **before the first response byte** is re-issued byte-identically, so the two requests fingerprint the same under `Rules.DEFAULT` and resume as designed works. A **mid-stream** drop is not: 31 to 47 ms later the client sends a fresh turn on a new connection with a `\n` appended to the last text block of the last `user` message and one new text block after it asking the model to carry on, everything else byte-equal, and the partial output it already holds sent nowhere. The difference is in `/messages/*/content/*/text` and in the length of `/messages/*/content` — the one field the fingerprint exists to tell requests apart by — and the spike proved through `POST /rules/test` that the only rule in today's vocabulary that closes it, an `ignorePointers` entry naming `/messages/*/content/3`, does so by deleting the fourth content block of every message of every conversation. That is the flaky-Wi-Fi case in story 21 and the expensive one: run 1 billed 715 output tokens for nothing and re-wrote 24,189 cache tokens because the appended block broke the cached prefix.

So `Rules.DEFAULT` does not change, the replay fingerprint does not change, and **resume gains a second way to match, owned by the surface rather than by the rule set**. Exact match: the re-issue's normalized fingerprint equals a buffered exchange's, on any surface. Continuation match, Messages only: the re-issue equals the buffered request in everything except the `content` of its last `user` message, and there the original's blocks are a prefix of the re-issue's, where the last original block may differ from its counterpart only by trailing whitespace in its `text` and everything appended after it is a `text` block. Candidates are found by a coarse key — the fingerprint of the normalized request with that one `content` removed, computed once per buffered exchange and once per incoming request — and the prefix relation is then verified block by block on the objects themselves; the coarse key never decides a match on its own. Nothing reads the wording of the client's nudge, which is a client constant that will move at the next release. This lives on `Surface` as `continuable`, defaulting to "exact only", which `Messages` alone overrides, so the interceptor has no `when (surface)` in it and the next surface earns a looser match by being measured.

Five further decisions the design left open, all built:

- **Eligibility.** An exchange becomes resumable when its client goes, not merely by being recent. Section 4 step 5 is what makes an exchange "eligible for Resume", and reading step 3 alone — any two equal requests inside five minutes are one — would silently stop a user re-asking the same question for a fresh sample. "Gone" is the engine's word on the connection as well as the flag the client writer sets, because the writer only looks between frames and a re-issue arriving 31 ms later can beat it there. A continuation match is offered only for an exchange whose client has gone, with no engine-word shortcut needed, since that drop is by definition mid-stream.
- **What is served.** The whole buffered answer from its first frame, not the tail the re-issue asked to carry on from: the client discarded its partial output, and the buffer holds the complete original. Live if the upstream is still streaming, which is the normal case at 31 ms.
- **One drop buys one resume.** A claim takes the exchange out of the buffer, so a second equal request goes upstream. One buffered answer served to every retry for five minutes would be worse than the waste it replaces, and a user who does want a fresh sample gets one on the second ask. A laptop that sleeps twice is still covered, because the resumed exchange is tracked like any other and becomes claimable itself when its own client goes.
- **A broken answer is never served as a whole one.** An upstream cut short does not raise anything: the provider's socket simply ends and the frames that arrived look like any other frames, so the only thing that says an answer is whole is that the surface's own terminal frame is among them. `Surface.terminates` says which frame that is — `message_stop`, `data: [DONE]`, `response.completed` or `.incomplete`, or a non-streaming body — and defaults to "never", so a surface nobody has taught cannot have a cut answer taken for a complete one. A provider *error* event does not terminate: a client asking again is owed a fresh ask. A re-issue that joined while the answer was still streaming instead shares its fate, cut exactly where the original was cut, which is the stream the provider would have given the client itself.
- **What a resumed exchange costs.** 0, for the same reason a replay hit costs 0 (section 7): it made no upstream call, so it was billed nothing. Its usage is the answer's, read from the frames as any line's is. The call and its cost sit on the line of the exchange it was resumed from, the one that says `clientDisconnected`. It is its own row in the store, keyed by its own ULID, overwriting nothing. `resumed` lives on the event line and **not** in the store: section 6's schema rule says the tables are never altered before v1, so a fourth flag column would refuse to open every database that already exists. Anything asking which exchanges were resumed asks `events.jsonl` or the `event` table. One consequence of it being a real row: in record mode it stores the same answer a second time under the same fingerprint, so a `repeatPolicy = "inOrder"` replay of that session serves that answer twice before its cursor moves on. A recorded retry sequence that was resumed replays one step out of step; `latest` is unaffected.

## Considered options

- **A fourth rule type: drop an array element matching a predicate.** It would let `rules.json` express the difference and keep resume on plain fingerprint equality. Set aside because it widens the rule language — the thing `POST /rules/test` exists to keep people safe from — permanently, for one client's one string, and because the rule would still have to be *written* by whoever ships the defaults and would still merge two genuinely different requests wherever a real turn ends in an appended text block. `CLAUDE.md` says a new rule or mechanism is raised and not added; this is the version of it that never has to be raised again.
- **The index pointer.** `ignorePointers: ["/metadata", "/stream", "/messages/*/content/3"]`, which the spike tested through the proxy's own `/rules/test`: exactly the two mid-stream pairs collapse and nothing splits over the eight recorded exchanges. Rejected there and rejected here — it deletes the fourth content block of every message of every conversation, so the moment a real turn has four blocks two different requests replay as one.
- **Ship resume for the pre-first-byte drop only.** The smallest honest option, and what #26 would have been without this ADR. Set aside because it leaves the more expensive of the two drops uncovered: mid-stream is where the partial output is furthest along, and it is the one story 21 was written for.
- **Change the replay fingerprint instead.** Rejected outright. Replay must keep telling those two requests apart: they *are* different requests, and a cassette that answered both with one recording would be wrong.
- **Serve only the tail from the drop point.** The client asked to carry on from where it stopped, so serving the remainder looks like the literal answer. Rejected because the client throws its partial output away — `/messages` is `array[2]` in the re-issue, with no assistant turn — so a tail would be all it ever saw of the turn.

## Consequences

- `Rules.DEFAULT` is byte-for-byte what it was, and every existing fingerprint and cassette still matches. `RulesTest` and the replay seam tests are the proof; the `Rules.kt` change is an extraction only, splitting `fingerprint` into `normalized` plus `fingerprintOf` so the coarse key is hashed by the same code.
- The proxy holds the frames of every tracked answer in memory for the window. The ceiling is (`resume.maxBufferedExchanges` + the exchanges in flight) × the size of an answer: the cap bounds only the answers whose clients have gone, because an exchange still streaming to a client who is still there is not buffered for anyone yet and is let go at its completion. The `ponytail:` in `Resume.kt` says the same and carries the upgrade path.
- `Exchange` carries three more fields: `normalized` and `clientGone`, both set at classify by the relay so no interceptor applies the rules a second time or waits for the client writer to notice a departure, and the `resumed` flag the event line reads.
- A false positive would serve one client another client's answer. The surface of it is: two requests whose stems hash the same **and** whose last user content stands in the prefix relation **and** one of whose clients has just gone. The stem is compared by its SHA-256 alone, which is the trust an equal replay fingerprint already asks for; everything else is compared on the objects.
- That surface is widened by two things resume **inherits** from `Rules.DEFAULT` rather than adds, and which are worth naming because replay only ever meets them on a replay route while resume meets them on live traffic. `ignorePointers` erases `/metadata` before the hash, and that is where Claude Code puts `user_id`, so two users sending the same request are one request here; and it erases `/stream`, so a `stream: false` re-issue of a `stream: true` original matches, and would be served the original's SSE frames under its `text/event-stream` headers. The eligibility gate is what holds both back — the original's client must have gone — and neither is a reason to change the defaults, which replay depends on. Whether resume should refuse a claim whose asker disagrees with the buffered response about `stream` is a question for the owner, not a rule to add here.
- The farm reducer has not been taught about any of this. Two `exchange.completed` lines now carry the same `usage` and the same `stopReason` for one provider call, and `app/.../farm/Signals.kt` counts produce and adds tokens on any completed `end_turn` with a 2xx, so a resumed answer drops two harvests and doubles that turn's tokens on the end-of-day card. The cost ledger is right (0.0 adds nothing) and the water is right by accident (the original is a spill, because its client left). `resumed` is on the line for the reducer to read; filtering on it is `app`'s change and not this one's.
- Resume on the Responses surface — its own sequence numbers and `starting_after` served from the buffer — is still #27. What #27 inherits is `FrameLog`, which is the "read from frame 0 while the owner appends" primitive a cursor is a filter on, and `Surface.terminates`.
- **`docs/design.md` §13's "The design does not change" did not survive spike 1.** The As-built paragraph for #26 in §9 says so in the document itself.

## Backing it out

Delete `core/.../Continuable.kt`, the `continuable` member of `Surface` and its `Messages` override, and the `reissuedAs` continuation branch in `Resume.kt`. Resume then matches on an equal fingerprint alone, which is what §9 describes, and covers the pre-first-byte drop and nothing else; `ResumeMatchTest` goes with it and `ResumeSeamTest` still passes unchanged. Nothing is stored, exported or replayed differently either way — no cassette, no row and no event field records that a continuation was matched rather than a fingerprint — so backing it out needs no migration and invalidates no recording.
